# Agent 代码质量优化任务清单

日期：2026-11-17；实施验收更新：2026-11-18，Asia/Singapore。状态：用户授权的 T1–T3 已完成框架实现与回归；T4–T9 尚未启动。

本轮优先目标是消除已确认的整类错误、建立可执行的功能地图、验证测试能发现错误，并持续度量效果。以下九项形成一次完整交付；TLA+/Lean 等形式验证作为后续按风险选用的能力。

事实基线见[源码研究与探针报告](../.artifacts/grok-quality-research-20261117/assessment.md)。该规划基线当时绑定 15 个源文件；此前 32 项定向回归通过，47.80 秒，两个检查器探针分别暴露误报和漏报。这些是改前资料。当前实现与验证见本文件的实施回执，不把历史结果当成改后结果。

## 交付目标与约束

将同一候选的需求、状态与事件、接口/依赖规则、实际检查、必要终端旅程和最终验收结果关联起来。已有 DAG、监督器、候选摘要、必要用例、阻断项、重试和事件记录继续作为基础。

核心假设：精确的约束和真实行为验证能够降低所覆盖错误的复发与漏放。现有流程与证据控制已经存在，当前可见的限制是检查器判定不准确、共享技术栈与目标路径不一致，以及业务行为未充分绑定实际执行。任务完成后用固定正反例和可比样本重新判断，不能用总测试数或 AI 评分替代效果证据。

必要验收须全部满足：固定坏候选没有错误放行；合法基线全部可以通过；必要用例实际执行覆盖 100%；漏项、跳过、工具错误、候选漂移和未关闭阻断均不能升级为项目通过。上述阈值限定于声明的验收集合，不承诺所有未知缺陷归零。

每个任务是可独立验证的行为切片，不按“先改完所有 schema，再改完所有脚本”横向拆分。任务依赖只表示必需前提，实施顺序不等于强制依赖。

## T1 — 让现有检查正确识别合法与违规候选

**交付行为：** 从流水线实际入口执行完整性检查，正确识别已复现的空函数问题，并保留真正的工具错误。

**Blocked by：** 无。

- [x] 先保存现有合法/违规探针、候选身份、实际退出码和日志作为改前基线。
- [x] 有返回语句的正常多行函数通过；声明为禁止的空桩被拦截；业务允许的空回调有受限、可审查的例外。
- [x] 复用适合目标语言的已有解析器或 linter；不再用函数首行推测完整函数体。
- [x] 修复默认脚本路径；通过正式执行入口验证工作目录和脚本解析，无需真实模型调用即可验证框架控制流。
- [x] 工具缺失、语法解析失败、命令非零退出与“没有违规”分开记录；必要检查无法执行时不能通过。

## T2 — 把一条功能从 S1 贯通到实际验收

**交付行为：** 一条需求通过可执行功能地图找到检查动作、业务断言和最终结果；地图缺少必要行为时，交付不能关闭。

**Blocked by：** 无，复用现有监督器及项目验收接口。

- [x] 复用既有需求/验收 ID，关联功能、角色、前提、状态、事件、数据变化、失败/重试及页面反馈。
- [x] 每项必要行为绑定执行目标、稳定用例 ID、实际检查命令或驱动、预期可观察结果和证据位置。
- [x] 开始执行前冻结地图版本、必验集合与对应验收合同；事后删项或改预期使相关旧证据失效，不能消除原阻断义务。
- [x] 从一条 API 行为完成 S1 → 检查执行 → 结果收集 → 最终判定的完整路径；合法结果可通过，失败/缺失/skip 不能通过。
- [x] 不另建第二个验收引擎；将功能地图所声明的必要行为映射到现有项目验收合同。
- [x] 老任务的兼容路径保留，未配置新验收范围时不得自动获得新的产品接受结论。

## T3 — 从第一次尝试记录五类效果数据

**交付行为：** 同一任务即使多次失败后通过，报告仍显示首次结果、全部返工和累计成本，可按技术栈、风险和任务规模比较。

**Blocked by：** T2。T1 及后续任务开始时即保留现有原始执行事件，不能等汇总功能上线后才补记分母。

- [x] 复用现有 run/attempt、事件和费用记录，建立稳定任务身份及候选/合同关联；保留首次失败，不被后续绿色结果覆盖。
- [x] 五类指标按下文定义计算，零分母、缺失数据和无法确认的业务预期输出 unavailable，不能默认 0 或 100%。
- [x] 作者自检、独立验收、框架夹具、真实业务运行分别统计；模拟模型运行不成为自治效果样本。
- [x] 实际费用、估算费用、主动执行耗时与授权等待分开；成功任务累计成本包含此前失败尝试，同时报告未完成任务成本，避免幸存者偏差。
- [x] 重放、恢复和重复读取不重复计数；改变模型、预算、任务范围或观察窗口会标记为不可直接比较。

## T4 — 按模块和终端运行正确的检查

**交付行为：** 混合技术栈项目的每个模块使用自己的命令和工作目录，结果归属到正确候选与目标。

**Blocked by：** 无。可以先用已有项目命令验证，再补必要的最小配置表达。

- [ ] 支持项目声明模块路径、技术栈、检查命令、相关依赖锁与交付产物；优先复用项目现有脚本。
- [ ] Java 后端与 JS/TS 前端的混合样本分别执行各自工具；Python 样本不接受 Java 专用检查替代。
- [ ] 配置覆盖顺序明确，显式选择技术栈后，编译、lint、测试及覆盖率使用一致配置。
- [ ] 空检查集合、错误工作目录、未知模块或工具错误不能产生该目标的通过结论。
- [ ] 将 Spring 注解、每列表导出、固定种子数据等项目专用规则移到明确适用范围；公共提示词按已批准需求生成代码。
- [ ] 对尚未实际验证的语言/终端明确标注未验证，不以配置项存在宣称已支持完整交付。

## T5 — 将已确认的整类错误变成架构与合同规则

**交付行为：** S2 声明的接口与依赖约束在 S3/S3b 的真实代码和构建结果上得到检查，违反约束时自动阻断并返回可定位原因。

**Blocked by：** T2、T4。

- [ ] 第一组覆盖：禁止的跨层/跨进程依赖、请求响应字段漂移、生产路径误接演示数据或假接口。
- [ ] 合同对齐以实际序列化/API 语义为准，允许明确的合法字段转换，不要求所有内部变量同名。
- [ ] 测试夹具、文档样例及获准的模拟场景与生产路径区分；不通过全局禁止计时器、注释或 any 等字符串实现规则。
- [ ] 每条规则有稳定 ID、适用目标、来源、失败说明、合法样本、违规样本和边界样本。
- [ ] 从正式执行入口证明违规不能被 AI 均分抵消；合法样本不会被误拦；规则、合同或候选变化时相关旧证据失效。
- [ ] 仅扩充有现实缺陷或明确架构约束支持的规则；新错误类经回归验证后局部纳入，不自动写入全局 Skill 或指令。

## T6 — 验证失败、并发、重试和真实副作用

**交付行为：** S4 系列除正常路径外，能证明一个重要业务行为在失败和竞争条件下仍满足约定不变量。

**Blocked by：** T2。

- [ ] 选择一个有明确业务预期的代表行为，覆盖重复请求、并发竞争、超时/响应丢失、重试和非法输入。
- [ ] 断言实际数据库/队列/文件等相关副作用，不用 HTTP 200 或模拟返回值替代业务结果。
- [ ] 保留测试数据隔离与执行顺序证据；需要同会话验证的场景不能拆成独立环境冒充。
- [ ] 原始失败可复现，修复后同一路径通过；错误候选会失败，合法候选能通过。
- [ ] 对适合的关键状态加入属性/操作序列测试；保留随机种子、最小反例、工具版本和环境。
- [ ] 高风险行为由独立验收者核对业务预期和原始结果；角色标签本身不能证明独立性。

## T7 — 必要终端旅程必须真实执行

**交付行为：** S4e 按功能地图执行项目声明的 PC Web、H5、桌面或移动端旅程，并把实际观察关联到 API 与数据状态。

**Blocked by：** T2、T4。

- [ ] 首个实际支持的终端完成一条登录后关键旅程，并验证失败/重试与页面反馈；随后按项目需求扩展目标。
- [ ] 浏览器、真实 WebView、原生安装包和 Electron 包分别记录目标身份；结果不跨终端冒用。
- [ ] 必要旅程的工具缺失、环境不可用、零步骤或 skip 保持未验证；只有合同事先声明的不适用项可以排除。
- [ ] Trace、截图、请求、错误与相关数据读回绑定同候选和同次运行；截图本身不代替业务断言。
- [ ] 对性能要求明确的旅程实际测量约定指标；生成基准配置或分析报告不能冒充测量完成。

## T8 — 用变异验证关键测试能发现错误

**交付行为：** 对指定的重要逻辑故意引入行为错误，检验对应测试是否确实失败，结果进入该候选的验收证据。

**Blocked by：** T2、T4。

- [ ] 先证明原始候选通过相应用例，再在隔离副本中执行变异；原候选及验收预期保持不变。
- [ ] 首组变异针对已确认的重要性质，例如错误边界、缺失权限判断、移除幂等保护或漏写持久化结果。
- [ ] Java 可接现有 PIT；其他语言先接项目已有工具或范围明确的受控错误变体，不要求统一安装全套工具。
- [ ] 分开记录 killed、survived、等价候选、无效变异、执行错误和超时；编译失败或工具崩溃不算测试成功发现业务错误。
- [ ] 已确认且非等价的关键错误变体全部被目标断言发现；整体变异分数仅作为辅助，不能抵消关键存活变异。
- [ ] 固定目标、样本和预算；只覆盖关键逻辑，不默认全仓库全量变异。

## T9 — 同候选整链验收与可比效果试点

**交付行为：** 九项优化通过一份可审计交付回执，分别报告框架能力、实际项目结果和可测量的效果。

**Blocked by：** T1–T8。

- [ ] 固定合法/违规候选、保留样本、需求与用例集合；使用正式执行入口验证 S1 → S2 → S3/S3b → S4 系列 → S4e → 最终判定。
- [ ] 一份合法同候选被接受；已知必要失败、漏项、旧报告、源/包/配置漂移和 open 阻断全部拒绝。
- [ ] 验证恢复、重放及报告一致性，保留首次失败和历史阻断；每次修复后只重跑受影响且必须更新的证据。
- [ ] 固定模型/工具预算、按技术栈、风险和变更规模分组；纳入没有通过的任务，比较五类指标并说明样本与观察窗口。
- [ ] 将确证且可复用的缺陷补为本项目回归或局部规则，记录修复前红灯和修复后绿灯；不把阶段成功直接记成产品成功。
- [ ] 对实现做 Standards 与 Spec 两类复核；每个未关闭问题有责任范围、证据和下一动作。
- [ ] 框架夹具验收与真实业务试点分别报告。真实项目、模型数据边界和费用预算须在其既有授权范围内；本清单不自动启动独立的 AM-ISO-01，也不扩大到 AI Market 产品修复。

## 五类指标的固定口径

| 指标 | 口径 |
| --- | --- |
| 已知坏候选漏放率 | 被错误接受的已确认坏候选 / 已执行的已确认坏候选；坏候选预期来自冻结且独立复核的反例集合 |
| 合法候选误阻断率 | 被规则错误拒绝的合法候选 / 已执行的合法候选；业务失败、环境失败与规则误报分别归因 |
| 同类缺陷复发率 | 固定后续观察集合中，同一已处理错误类别再次出现的合格任务数 / 该规则适用且已观察的任务数；同时保留缺陷计数 |
| 首次独立验收通过率 | 首次候选通过独立验收的任务 / 首次独立验收已有终态结果的任务；同时列出纳入总数、未送审与待验数，防止选择性送审；修复后重送不产生新的首次样本 |
| 每个被接受任务的返工与总成本 | 从首次尝试至独立接受的全部修复轮次、人工技术干预、主动耗时和可核验费用；同时列出未完成任务消耗及估算项 |

指标不得混合框架夹具、真实模型任务和产品上线结果；按技术栈、风险、任务规模、模型/工具版本和预算分层。回退率只作补充，不能代替缺陷率；短期零事故不能证明长期可靠。

## 执行顺序、范围与停止线

建议顺序：**T1 → T2 → T3 → T4 → T5/T6/T7/T8 → T9**。T3 较早完成以保证改进过程中留下可比数据；T5–T8 有独立责任边界时可单独排期，不表示已授权启动多个 Agent。

源码实现继续使用现有集成分支，保留无关工作，每项按独立可解释和可回退的变化提交。任务卡列表不替代外部推送、发布或真实模型外发授权。

后续选项：复杂状态协议的 TLA+、关键算法的 Lean、长周期外围探索和扩大自主合并范围。它们在本轮基础行为与效果证据成立后再决策。保留必要注释，不实施全局注释清除或跨项目禁用某一 API。

若合法候选持续误拦、坏候选漏放、预期被削弱、数据分母丢失、候选/运行环境无法对应或成本超过既定预算，保留反例并停止扩大自治范围。修正对应规则或接入路径后重新测量，不以提高 AI 分数、删测或反复重跑到绿替代修复。

T1–T3 的框架实现与固定样本已验证；真实业务效果试点仍需锁定具体项目、独立预期、模型/工具版本、观察窗口及允许的运行环境。没有真实模型自主交付、生产发布或缺陷率下降的新完成声明。

方法记录：复用已读 `ask-matt` 路由，本轮读取并应用 `to-tickets` 的可独立验证切片与阻塞依赖规则；当前为任务草案，未发布为外部 ready-for-agent 工单。读取 Claude saved 的前端质量闸与实测纪律，只借用错误类别和证据要求，未直接复制未经当前代码验证的 grep 命令或历史效果数字。无需新增全局 Memory、Skill、Hook 或 AGENTS 规则。
