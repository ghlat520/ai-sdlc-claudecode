## 问题、基线与根因

修正版试点在用户调整执行范围后已终止，但冻结执行器的状态仍是
`running`／S20 `running`。先在当前工具版本重新构造同一信号路径，
避免把旧快照的问题直接归给当前实现。

通过真实 `pipeline-executor.sh` 启动本地阻塞模型替身，对其执行进程组发送
SIGTERM；干净红灯用例在 1.08 秒内确认状态仍为 `running`。证据位于
`.artifacts/quality-interruption-20261118/red-actual.xml`。

根因是直接 Bash 入口只在正常流程末尾调用 `finish`，没有进程退出落盘路径。
Python Runner 已有 `record_executor_exit`，直接 Bash 运行没有使用它。
因此中断会绕过正常收尾，遗留活动阶段和 owner 状态。此结论不等于
断言试点外层账本的 130／143 差异也由同一处代码造成；历史差异继续保留。

## 最小修复

- Bash 在成功取得运行所有权后，为直接调用补充 invocation ID，并安装
  EXIT／SIGINT／SIGTERM 处理；退出码保留为 130／143 等实际含义。
- 复用现有锁定、原子状态写入，通过 run＋invocation 匹配记录执行器退出。
  非成功退出只把当前 run 尚在执行的阶段标为失败，保留既有证据和已完成阶段，释放 owner。
- 子阶段的并行 subshell 不拥有流水线终态，不能提前替父执行器写入最终结果。
  旧 run 或其他 invocation 的收尾写入仍被拒绝。
- 保留等待、暂停、部分执行及产品验收的独立语义，不新增执行模式、验收开关或重试。
